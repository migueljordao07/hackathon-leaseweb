# BlastShield: Pre-Flight AST Blast-Radius Engine for Safe Infrastructure Operations

> For **on-call engineers and DevOps teams operating stateful Linux workloads on sovereign cloud VMs**, we help **prevent catastrophic accidental data loss and cascading outages caused by unvetted AI/CLI fixes** using **static shell AST blast-radius decomposition and ephemeral cgroup sandbox dry-runs**, improving **safe execution certainty from high-risk guesswork to a mathematically bounded and tested operation**.

**Proposed by:** Francisco · **Status:** Shortlisted (Operational Safety)  
**Theme:** AI-assisted operations / Security & data protection  

---

## 1. Problem and user

- **Who encounters this, and when?**  
  On-call sysadmins and developers responding to outages or configuration drift on Linux VMs at 3 AM, or reviewing AI-generated infrastructure remediation scripts.
- **What goes wrong today?**  
  When an incident strikes, generalist AI assistants (Claude, ChatGPT, or terminal copilot wrappers) readily generate remediation shell commands like `docker system prune -af`, `rm -rf /var/run/*`, or `systemctl restart postgresql`.  
  **The fatal flaw:** These commands often possess an uncalculated **blast radius**. An engineer blindly executing the suggestion might destroy active persistent volumes, drop database lock files, or cause an uncontrollable cascading failure across downstream services. Because LLMs lack deterministic safety bounds, engineers legitimately distrust AI in production write paths.
- **Current workaround:**  
  Engineers refuse to execute AI suggestions, spending 45+ minutes manually verifying files and dependencies, or conversely, inexperienced operators run dangerous commands and accidentally trigger permanent data loss.
- **Evidence:**  
  - SRE practitioner surveys on Reddit (`r/devops` and `r/sre`) heavily emphasize the *"Read-Only vs. Write-Access Wall"*: organizations forbid autonomous remediation agents because there are zero deterministic rollback or sandbox verification gates.
  - Team research note: A generic chatbot that runs bash commands is redundant (Claude Code and Cursor already do this); true innovation lies in **deterministic blast-radius containment before execution**.

## 2. Proposed solution and AI contribution

- **User workflow:**  
  1. **Intercept:** An operator or incident responder receives a candidate fix command (generated by an AI assistant or human runbook).
  2. **Deterministic AST Decomposition:** BlastShield parses the command into an Abstract Syntax Tree (AST) using a hardened shell grammar. It inspects:
     - *State & Volume Boundary:* Does this command touch mount paths containing persistent data (`/var/lib/docker/volumes`, `/data`)?
     - *Process & Signal Scope:* Does it invoke `SIGKILL`, `drop_caches`, or ungraceful termination?
     - *Network Interruption:* Will open listening sockets be closed?
  3. **Ephemeral Digital-Twin Dry-Run:** If the command passes static AST safety rules, BlastShield spins up a scratch cgroup/container mirror on the Linux VM, runs the command inside the sandbox, and executes automated health probes.
  4. **Evidence-Backed Approval Card:** The dashboard displays:
     - 💥 *Blast Radius Breakdown:* Data Loss Risk: 0.0% (No stateful paths touched). Affected processes: 1 container.
     - 🧪 *Sandbox Dry-Run Evidence:* "Tested in isolated container in 2.1s: Service restarted, HTTP 200 returned, zero disk corruption."
  5. **Safe One-Click Production Apply:** The human confirms execution with confidence.
- **What AI adds:**  
  Analyzes unstructured application logs to determine appropriate post-execution health verification criteria, and formulates context-aware rollback scripts if the primary command produces side effects.
- **Simple baseline:**  
  Executing raw shell commands directly in the host terminal without pre-flight syntactic safety checks or sandboxing.
- **Action boundary:**  
  - **Read:** Shell command string, host filesystem mount tables, cgroup limits, and Docker configuration.
  - **Sandbox:** Executes exclusively inside an unprivileged, ephemeral scratch container with read-only host mounts.
  - **Production Apply:** **Strictly gated behind explicit human approval in the UI.** No autonomous host writes.

## 4. Smallest working demo

**Demo story:**  
A developer on the Leaseweb VM is handling a broken microservice and considers running a cleanup command suggested by an AI assistant.

1. **Before:** The user pastes a risky candidate command (e.g., `docker compose down -v && docker compose up -d`).
2. **Intervention:** BlastShield flags the dangerous `-v` flag via AST parsing: *"CRITICAL ALERT: Command requests volume deletion on stateful service `postgres_data`! Blast radius: Complete data loss."* BlastShield automatically strips the destructive flag, runs a safe restart in an ephemeral sandbox, and verifies the database responds cleanly.
3. **After:** The user sees the visual safety breakdown and clicks **"Execute Safe Remediated Plan"**. The service recovers with zero data loss.

- **Must build:**  
  1. A Python shell AST parser (using `shlex` / `bashlex`) flagging destructive flags (`-v`, `rm`, `mkfs`, raw wildcard drops).
  2. A lightweight ephemeral container runner creating a 3-second scratch dry-run environment.
  3. A web UI (FastAPI/Streamlit) with the Blast Radius Risk Meter (Green/Yellow/Red) and the "Approve" button.
- **Out of scope today:**  
  Multi-node Kubernetes cluster federation, distributed eBPF tracing across physical networks.
- **Success metric:**  
  Correctly detect and block 100% of destructive volume/data commands while validating safe restarts in <4 seconds.
- **Failure case:**  
  If AST parsing fails on an obfuscated shell command, BlastShield defaults to **Fail-Closed** (blocks execution and requires manual root shell intervention).
- **Demo fallback:**  
  Deterministic test harness with 3 pre-configured incident scenarios (safe restart, memory tune-up, and blocked destructive data wipe).
