## 1. Problem and user

- **Who encounters this, and when?**  
  Platform engineers, CISO compliance leads, and sysadmins who have deployed infrastructure on European cloud providers (e.g., Leaseweb bare metal or public cloud VMs) believing their workloads are 100% sovereign and compliant with the EU NIS2 Directive (Article 21) and DORA.
- **What goes wrong today?**  
  Deploying a VM in Frankfurt or Amsterdam does **not** guarantee digital sovereignty. In reality, standard Linux setups and modern container stacks silently leak data, queries, and telemetry across the Atlantic:
  1. Default OS/Docker DNS resolvers route queries to Google (`8.8.8.8`) or Cloudflare (`1.1.1.1`), exposing operational access patterns.
  2. Popular runtime dependencies (pip, npm, APM agents, analytics SDKs, Docker base image maintainers) contain embedded background telemetry shipping operational metadata to US-controlled AWS/GCP data centers.
  3. Outgoing TLS handshakes connect to sub-processors subject to the **US CLOUD Act** and FISA 702.
  Current static linters (like Terraform scanners) only inspect declarative text files; they are blind to dynamic, runtime network telemetry.
- **Current workaround:**  
  Manual consultancy audits (paying €20k+ to Big Four audit firms) that rely on static questionnaires, or blind network blackholing that inadvertently breaks critical production integrations.
- **Evidence:**  
  - European Commission & ENISA reports emphasize that extra-territorial data transfers via telemetry represent a major non-compliance vector under NIS2.
  - Team research note: Existing team ideas in `Ricardo/` and `Diogo/` inspect static IaC or SDK source code; none inspect live Linux kernel socket states or runtime process traffic.

## 2. Proposed solution and AI contribution

- **User workflow:**  
  1. **Listen:** A lightweight Linux daemon continuously samples active network connections, outbound socket bindings (`/proc/net`, `ss`), and DNS queries generated by host processes and Docker containers.
  2. **Reason:** The AI engine analyzes destination IPs, reverse-DNS hostnames, TLS Server Name Indications (SNI), and owning ASN organizations. It cross-references them against geopolitical entity databases and legal jurisdiction frameworks to flag entities legally subject to the US CLOUD Act.
  3. **Score:** The dashboard renders a real-time **European Sovereignty Index (0–100%)** and visualizes an active world radar map highlighting non-compliant outbound leaks.
  4. **Enforce (Human-in-the-Loop):** The operator clicks **"Enforce Sovereign Shield"**. SovereignKernel instantly:
     - Updates host and container `/etc/resolv.conf` to privacy-hardened European sovereign DNS (e.g., `DNS0.eu` / Quad9 Swiss foundation).
     - Injects targeted `iptables / nftables` drop rules for non-essential telemetry endpoints.
     - Re-routes critical traffic via encrypted sovereign relays.
  5. **Verify & Certify:** Outbound leaks drop to 0, the Sovereignty Index reaches 100%, and an auditable **NIS2 Article 21 Compliance Certificate** is auto-generated with timestamped kernel evidence.
- **What AI adds:**  
  Disambiguates obscure CDN-fronted IPs, resolves nested SaaS parent company jurisdictions, distinguishes benign application API traffic from non-consensual telemetry leaks, and formulates precise iptables rules without breaking application functionality.
- **Simple baseline:**  
  A static `netstat` script piping to a hardcoded geo-IP database, which misses cloud CDN ownership, cannot reason about corporate legal jurisdiction, and cannot distinguish telemetry from core app traffic.
- **Action boundary:**  
  - **Read:** Outbound network sockets, DNS resolver configurations, process PIDs, and container cgroups.
  - **Recommend:** Geopolitical risk analysis, leaky process identification, and suggested firewall mitigations.
  - **Change:** Gated strictly behind a 1-click human confirmation in the UI; writes only to localized Linux firewall (`iptables`) and DNS config, with an automatic 30-second revert watchdog if network connectivity drops.

## 4. Smallest working demo

**Demo story:**  
A team runs a modern full-stack web application (FastAPI + Postgres + third-party analytics telemetry) inside Docker on the Leaseweb Linux VM.

1. **Before:** The VM administrator believes their setup is sovereign. SovereignKernel scans active sockets: the UI flags **Sovereignty Score: 44% (High Risk)**, showing live outbound streams leaking telemetry to `telemetry.segment.io` (AWS US) and DNS queries routing to Google `8.8.8.8`.
2. **Intervention:** The AI analyzes the streams, identifies the parent corporations and legal jurisdiction, and generates a two-step remediation plan: swap DNS to `DNS0.eu` and drop non-essential US telemetry sockets via `iptables`.
3. **After:** The user clicks **"Apply Sovereign Enforcement"**. Rules apply instantaneously. The live traffic radar updates in real time, the Sovereignty Score leaps to **100% Verified Sovereign**, the web app continues functioning without disruption, and an exportable NIS2 compliance audit log is generated.

- **Must build:**  
  1. A Python daemon collecting active sockets via `ss -tunp` and DNS queries.
  2. An LLM geopolitical classification engine mapping domains/ASNs to jurisdiction entities (EU vs. US CLOUD Act).
  3. A high-impact visual UI (FastAPI + Tailwind or Streamlit) showing the Sovereignty Index meter, leak breakdown, and the "Enforce" button.
  4. An iptables / DNS enforcement script with auto-rollback safety.
- **Out of scope today:**  
  Deep packet inspection of encrypted TLS payloads, hardware-level eBPF kernel modules (simulated via standard Linux socket polling).
- **Success metric:**  
  Detect active foreign leaks in <3 seconds; apply sovereign enforcement and restore 100% compliance score in <5 seconds.
- **Failure case:**  
  If blocking an endpoint causes application health probes to fail, the automated watchdog rolls back the `iptables` drop rule within 10 seconds and alerts the operator.
- **Demo fallback:**  
  Pre-captured socket logs and deterministic domain jurisdiction lookups to ensure the demo functions seamlessly if external network access fluctuates.

## 6. Fastest validation

- **Riskiest assumption:**  
  Can standard Linux commands (`ss -tupn`, `/proc/net`) expose container-level foreign connections quickly and reliably without needing kernel-level eBPF compilation?
- **Quick experiment:**  
  Run `ss -tupn` on the VM while a Docker container runs `curl https://www.google.com` and verify the socket IP is captured immediately.
- **Continue if:**  
  The remote IP and process ID are captured within 500ms.
- **Simplify or park if:**  
  Socket visibility requires root network namespaces that are restricted on the VM.
